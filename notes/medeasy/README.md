# [프로젝트 회고] 메디지(MedEasy) — 디자인부터 개발, 그리고 출시 준비까지

2025년, 약 1년에 걸쳐 진행했던 프로젝트 **메디지(MedEasy)**.

메디지는 디지털 기기 사용이 익숙하지 않은 고령자를 위한 AI 기반 복약 관리 서비스다. 대학교 졸업전시를 위해 시작한 팀 프로젝트였지만, 교내외 공모전에서 수상하고 실제 앱스토어 출시까지 준비했던 만큼 개인적으로도 많은 시간을 쏟았던 프로젝트다.

특히 팀 내 유일한 디자이너이자 프론트엔드 개발자로 참여하면서, 디자인한 화면이 실제 서비스로 구현되기까지 얼마나 많은 부분을 고려해야 하는지 배울 수 있었다.

## 01. 졸업전시에서 시작된 프로젝트

메디지는 대학교 4학년 1학기 말에 예정된 졸업전시를 위해 시작한 프로젝트다.

전 학기에 함께 팀 프로젝트를 진행하면서 합이 잘 맞았던 컴퓨터공학과 선배와 다시 팀을 꾸리기로 했고, 에브리타임에 팀원 모집 글을 올려 나머지 멤버들을 모집했다.

다만 생각보다 팀원 모집이 순조롭지는 않았다. 원하는 인원을 모두 모으기까지 시간이 걸렸고, 이미 주제를 정하고 개발을 시작한 다른 팀들에 비해 출발이 늦어지기도 했다.

최종적으로는 백엔드 개발자 2명, 프론트엔드 개발자 3명으로 구성된 5인 팀이 완성되었다. 나는 프론트엔드 개발과 함께 프로젝트의 UX/UI 디자인 전반을 담당하게 되었다.

## 02. 어떤 문제를 해결할 것인가?

프로젝트를 시작하면서 가장 먼저 고민한 것은 주제 선정이었다.

졸업작품인 만큼 기술적으로 도전할 수 있는 주제도 중요했지만, 팀원 모두가 필요성에 공감할 수 있는 사회문제를 해결하는 서비스를 만들고 싶었다.

여러 가지 아이디어를 이야기하던 중 나온 것이 '약 복용'에 관한 문제였다.

약을 먹어야 한다는 사실을 깜빡하거나, 이미 약을 먹었는지 기억이 나지 않았던 경험은 팀원 대부분에게 있었다. 처음에는 단순히 약 먹는 시간을 알려주는 앱을 생각했지만, 데스크 리서치를 진행하면서 문제가 생각보다 복잡하다는 사실을 알게 되었다.

특히 고령층은 만성질환 등으로 여러 종류의 약을 복용하는 경우가 많아 약마다 다른 복용 시간과 횟수를 관리해야 하는 어려움이 있었다. 여러 약을 함께 복용하면서 발생할 수 있는 병용금기나 중복 복용의 위험도 고려해야 했다.

기존에도 복약 관리 앱은 존재했지만, 정작 복약 관리가 필요한 고령층에게는 작은 글씨나 복잡한 입력 과정 자체가 진입장벽이 될 수 있었다.

그렇다면 **약을 등록하는 과정부터 매일 복용 여부를 확인하는 과정까지, 최대한 간단하게 만들 수는 없을까?**

이 질문에서 메디지의 방향이 구체화되기 시작했다.

## 03. 약을 챙겨 먹는 일을 조금 더 쉽게

처음 구상했던 기능은 비교적 단순했다.

사용자가 처방받은 약을 앱에 등록하면 복용 시간에 맞춰 알림을 보내고, 약을 먹었는지 기록할 수 있도록 하는 것이었다.

하지만 고령자를 주요 사용자로 설정한 만큼, 단순히 기능을 제공하는 것만으로는 부족했다. 약의 이름을 정확히 기억하지 못하거나 스마트폰의 작은 입력창을 사용하는 데 어려움을 느끼는 상황도 고려해야 했다.

이러한 문제를 해결하기 위해 다양한 기술을 활용했다.

**음성 대화 기반 복약 관리**

OpenAI의 GPT 모델과 LangGraph, MCP를 활용해 사용자가 자연어로 복약 정보를 조회하거나 일정을 등록할 수 있도록 했다. 음성 인식과 음성 합성에는 네이버 Clova Voice를 사용했다.

**처방전 촬영을 통한 약 등록**

처방전이나 약봉투를 촬영하면 Clova OCR로 약 이름과 복용 횟수, 기간 등의 정보를 추출하고 복약 일정에 반영하도록 했다. 약이 여러 종류일 때도 하나씩 직접 입력하지 않아도 된다는 점에 중점을 두었다.

**알약 이미지 검색**

약 이름을 모르는 상황에서도 알약의 사진만으로 의약품을 검색할 수 있도록 했다. Vertex AI와 식약처 공공데이터, Elasticsearch를 활용했으며, 이미지 전처리와 검색 로직 개선을 반복하면서 최종적으로 약 96.6%의 검색 정확도를 달성했다.

**NFC 기반 복약 기록**

매번 앱을 열어 복용할 약을 찾아 선택하는 과정도 줄이고 싶었다. NFC 카드를 스마트폰에 태그하면 복약 완료를 기록할 수 있도록 구현했다.

**보호자 연동 및 알림**

고령자 본인뿐 아니라 보호자도 복약 일정을 확인할 수 있도록 계정 연동 기능을 구현했다. 복용 시간을 놓쳤을 때 알림을 전달하고, 보호자가 대신 일정을 등록할 수 있도록 했다.

모바일 앱은 React Native와 TypeScript로 개발했고, 서버는 Spring Boot와 FastAPI를 중심으로 구성했다. 네이버 클라우드의 Kubernetes 환경을 활용해 서비스를 운영할 수 있도록 인프라도 구축했다.

처음에는 단순한 복약 알림 앱에서 출발했지만, 개발을 진행하면서 약을 등록하고 검색하는 과정부터 복용 기록과 보호자 관리까지 지원하는 서비스로 발전했다.

## 04. 피그마에서는 완벽했는데, 실제 화면은 달랐다

나는 팀 내 유일한 디자이너로 메디지의 전체 UX/UI 디자인을 담당했다.

와이어프레임부터 화면 설계, 컴포넌트 제작, 프로토타입까지 Figma를 활용해 디자인했고, 동시에 프론트엔드 개발자로도 참여해 전체 기능의 약 30%를 구현했다.

디자인과 개발을 함께 담당하는 만큼 구현까지 고려한 디자인을 만들 수 있을 것이라 생각했지만, 실제로는 예상하지 못한 문제가 많았다.

가장 먼저 느꼈던 것은 **Figma에서 보기 좋은 화면과 실제 기기에서 자연스럽게 동작하는 화면은 다르다**는 점이었다.

Figma에서는 컴포넌트 간 간격이나 정렬을 정확하게 맞춰두었지만, 실제 React Native로 구현한 화면에서는 텍스트의 높이나 여백이 예상과 다르게 보이는 경우가 있었다.

더미 데이터와 실제 데이터의 차이도 컸다.

디자인 단계에서는 짧은 약 이름이나 간단한 설명을 넣어두었기 때문에 작은 영역으로도 충분하다고 생각했다. 하지만 실제 API를 연결하고 나니 의약품 이름이나 주의사항처럼 길이가 긴 데이터가 들어오면서 텍스트가 잘리거나 레이아웃이 무너지는 문제가 발생했다.

처음에는 정해진 화면 안에 데이터를 어떻게 배치할지만 고민했다면, 개발을 진행하면서는 데이터의 길이가 달라지거나 예상과 다른 값이 들어와도 화면이 정상적으로 동작하는지 확인해야 했다.

텍스트가 두 줄 이상으로 늘어날 때는 어떻게 표시할지, 데이터가 없을 때는 어떤 화면을 보여줄지, 내용이 많을 때는 어디까지 스크롤할 수 있도록 할지 등을 다시 설계해야 했다.

정적인 화면을 디자인할 때는 미처 생각하지 못했던 부분이었다.

## 05. 로딩 화면에도 정답이 있는 것은 아니었다

프론트엔드 개발에 참여하면서 가장 많이 고민했던 부분 중 하나는 API 응답 속도에 따른 사용자 경험이었다.

특히 이미지 검색이나 OCR, AI 응답처럼 외부 서비스와 통신하는 기능은 결과가 반환되기까지 시간이 걸리기 때문에 로딩 상태를 어떻게 보여줄지 결정해야 했다.

처음에는 단순한 원형 로딩 인디케이터보다 실제 콘텐츠의 형태를 미리 보여주는 스켈레톤 UI나 플레이스홀더가 더 좋은 사용자 경험을 제공할 것이라고 생각했다.

하지만 직접 구현하고 테스트하면서 생각이 달라졌다.

이미지가 거의 즉시 로딩되는 상황에서도 플레이스홀더를 표시하도록 했더니, 짧은 순간 플레이스홀더가 나타났다가 실제 이미지로 교체되면서 화면이 깜빡거리는 것처럼 보였다.

사용자를 기다리게 하지 않기 위해 추가한 요소가 오히려 앱이 불안정하게 동작하는 듯한 인상을 주고 있었다.

결국 로딩 시간이 아주 짧을 때는 인디케이터를 표시하지 않거나, 단순한 원형 인디케이터를 사용하는 편이 더 자연스러울 수 있다는 사실을 알게 되었다. 반대로 시간이 오래 걸리고 콘텐츠의 구조가 정해져 있는 화면에서는 스켈레톤 UI가 유용했다.

이외에도 검색 결과가 없을 때의 Empty State, 네트워크 요청 중인 상태, 긴 콘텐츠가 영역을 벗어나는 경우 등 다양한 상황에 대응하는 UI를 설계했다.

이 경험을 통해 로딩 UI라고 해서 무조건 복잡하거나 시각적으로 풍부한 요소가 좋은 것은 아니라는 점을 배웠다.

**중요한 것은 어떤 UI 패턴을 사용했는지가 아니라, 실제 응답 시간과 사용 맥락에 맞는 피드백을 제공하는 것이었다.**

## 06. 직접 구현하면서 이해하게 된 디자인의 제약

메디지에서는 회원가입과 로그인, 알약 이미지 검색, 처방전 검색, NFC 기능 등 프론트엔드의 여러 부분을 직접 구현했다.

서버에서 데이터를 받아 화면에 표시하는 과정부터 비동기 요청 처리, 로딩 상태 관리, 오류 상황에 따른 UI 변경까지 다루다 보니 디자인할 때의 관점도 달라졌다.

디자인만 할 때는 자연스러워 보였던 인터랙션도 실제로 구현하려면 여러 상태와 예외 처리가 필요했다.

예를 들어 사용자가 검색 버튼을 눌렀을 때는 단순히 검색 결과 화면으로 이동하는 것이 아니라, 요청 중인 상태와 검색에 성공한 상태, 결과가 없는 상태, 오류가 발생한 상태를 각각 처리해야 했다.

NFC처럼 기기 기능과 연동되는 경우에는 앱이 실행 중인지, 백그라운드 상태인지에 따라서도 동작을 고려해야 했다.

이렇게 개발 과정에 참여하면서 디자인 단계에서 어떤 부분을 미리 정의해두면 개발이 수월해지는지 조금씩 이해할 수 있었다.

무엇보다 인상적이었던 것은 개발을 고려한다는 것이 단순히 구현하기 쉬운 UI를 만드는 일은 아니라는 점이었다.

구현 과정에서 발생할 수 있는 제약을 이해하고, 그 안에서 사용자 경험을 최대한 유지할 수 있는 방법을 고민하는 것도 디자이너의 역할이라고 생각하게 되었다.

## 07. 졸업작품에서 외부 공모전 수상까지

약 1년에 걸쳐 개발한 메디지는 한성대학교 캡스톤디자인 모바일 부문에서 장려상을 수상했다.

처음에는 졸업전시를 목표로 시작한 프로젝트였지만, 오랜 시간 개발해 온 결과물을 이대로 마무리하기에는 아쉬움이 남았다.

기능도 상당 부분 구현되어 있었고 실제 기기에서 동작하는 앱까지 완성한 만큼, 외부 공모전에도 도전해 보기로 했다.

그렇게 참가한 것이 **제6회 개방형 클라우드 플랫폼(K-PaaS) 활용 공모전**이었다.

결과적으로 약 300개 참가팀 중 5위에 해당하는 특별상을 수상했고, 상금 200만 원을 받았다.

졸업전시를 위해 시작했던 프로젝트가 외부 공모전에서도 좋은 평가를 받았다는 점에서 뜻깊은 결과였다.

다만 프로젝트를 진행하면서 좋은 평가만 받았던 것은 아니다.

개발 기간 동안에는 AI 모델의 정확도나 기능 구현 난이도, 시스템 아키텍처와 같은 기술적인 완성도에 많은 관심을 기울였다. 그런데 컴퓨터공학부 교수님들의 피드백에서는 기능 자체뿐 아니라 경쟁 서비스와의 차별점, 사용자가 메디지를 선택해야 하는 이유, 서비스의 필요성을 어떻게 설명할 것인지에 대한 질문도 받았다.

처음에는 기술적으로 어려운 기능을 많이 구현하고 완성도 높게 동작하도록 만드는 것이 좋은 결과물이라고 생각했던 것 같다.

하지만 아무리 기능이 뛰어나더라도 사용자가 그 기능을 필요로 하는 이유가 명확하지 않다면 좋은 서비스라고 단정할 수는 없었다.

특히 복약 관리처럼 이미 다양한 서비스가 존재하는 분야에서는 새로운 기술을 적용했다는 사실만으로 차별점이 만들어지는 것은 아니었다.

**무엇을 구현할 수 있는지보다, 왜 이 기능이 필요한지를 먼저 설명할 수 있어야 한다는 점을 배웠다.**

개발 기술 중심으로 프로젝트를 바라보던 시각에서 벗어나, 좋은 프로덕트의 조건을 고민해 볼 수 있었던 경험이었다.

## 08. 앱스토어 출시를 준비했지만

공모전 이후에는 메디지를 실제 앱스토어에 출시하는 것을 목표로 준비했다.

Apple Developer 계정을 등록하고, 앱스토어에 사용할 스크린샷과 소개 자료를 제작했다. TestFlight를 통한 테스트 배포도 준비하면서 실제 사용자에게 서비스를 제공하기 위한 과정을 밟았다.

개발 단계에서 앱을 실행하는 것과 외부 사용자에게 정식으로 배포하는 것은 생각보다 다른 일이었다.

특히 메디지는 의약품과 복약 정보를 다루는 서비스였기 때문에 일반적인 앱보다 더 신중한 검토가 필요했다. 건강 및 의료와 관련된 정보의 정확성과 신뢰성, 사용자 데이터 처리 방식 등 고려해야 할 부분이 많았다.

결국 여러 가지 출시 요건과 부담을 고려한 끝에 정식 앱스토어 출시는 진행하지 못했다.

기능 구현부터 앱스토어 등록을 위한 준비까지 마친 상태였기 때문에 아쉬움이 컸다.

하지만 이 과정에서 한 가지를 더 알게 되었다.

**서비스를 개발할 수 있다는 것과 실제로 사용자에게 제공할 수 있다는 것은 별개의 문제였다.**

특히 의료정보처럼 민감한 데이터를 다루는 서비스에서는 구현 가능성뿐 아니라 정보의 신뢰성, 개인정보 보호, 플랫폼의 정책까지 제품 설계 단계에서 함께 고려해야 했다.

처음부터 출시를 염두에 두었다면 기술 개발에 집중하는 것과 동시에 이러한 조건도 더 일찍 조사했어야 했다는 아쉬움이 남는다.

## 09. 메디지를 마치며

메디지는 지금까지 진행했던 프로젝트 중에서도 특히 많은 시간을 투자했던 작업이다.

팀 결성부터 주제 선정, UX/UI 디자인, 프론트엔드 개발, 공모전 참가, 출시 준비까지 하나의 제품이 만들어지는 과정을 폭넓게 경험할 수 있었다.

처음에는 디자인한 화면을 그대로 구현하는 것이 중요하다고 생각했지만, 실제로 개발해 보니 화면은 데이터와 네트워크 환경, 기기의 상태에 따라 계속 달라졌다.

또 기술적으로 어려운 기능을 구현하는 데 집중하다가도, 정작 사용자가 왜 이 서비스를 이용해야 하는지에 대한 질문을 받으면서 제품을 바라보는 관점이 달라지기도 했다.

최종적으로 앱스토어에 출시하지는 못했지만, 두 번의 수상이라는 성과와 함께 디자인과 개발 사이의 간극을 직접 경험할 수 있었다는 점에서 의미가 컸다.

무엇보다 이 프로젝트를 통해 **구현의 제약을 이해하면서 사용자 경험을 설계할 수 있는 디자이너가 되고 싶다**는 생각이 구체화되었다.

Figma에서 완성된 화면을 만드는 것으로 끝나는 것이 아니라, 실제 데이터가 들어오고 사용자가 조작하는 환경에서도 자연스럽게 동작하는 제품을 설계하고 싶다.

메디지는 그런 생각을 갖게 된 첫 번째 큰 프로젝트였다.
