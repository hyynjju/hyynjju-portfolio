# [프로젝트 회고] 포트폴리오 웹사이트 리뉴얼 — Figma와 Codex로 4일 만에 완성하기

약 1년 전에 처음 제작했던 개인 포트폴리오 웹사이트를 새롭게 만들었다.

기존 사이트도 직접 디자인하고 개발했지만, 시간이 지나면서 프로젝트가 늘어나고 보여주고 싶은 내용도 많아졌다. 무엇보다 기존 사이트에서는 프로젝트를 한눈에 확인하기 어렵고, 새로운 작업을 추가하거나 기존 정보를 수정하는 데에도 생각보다 많은 시간이 필요했다.

이번에는 단순히 디자인을 새롭게 하는 것뿐 아니라 **콘텐츠를 쉽게 관리하고, 방문자가 원하는 프로젝트를 빠르게 찾을 수 있는 사이트**를 만드는 것을 목표로 했다.

Figma로 디자인하고 Codex Work를 활용해 개발했으며, 기획과 디자인에 2일, 개발에 2일을 사용해 총 4일 만에 완성했다.

이번 글에서는 포트폴리오 사이트를 리뉴얼하게 된 계기와 주요 기능, AI를 활용한 개발 과정에서 겪었던 시행착오를 정리해 보려고 한다.

## 01. 포트폴리오 사이트를 다시 만들기로 한 이유

기존 포트폴리오 사이트를 제작한 지 약 1년이 지났다.

그동안 새로운 프로젝트도 진행했고, UX/UI 디자이너로서 보여주고 싶은 역량이나 작업에 대한 생각도 조금씩 달라졌다.

하지만 기존 사이트에서는 프로젝트를 목록으로 비교하거나 원하는 작업을 찾기가 어려웠다. 프로젝트가 추가될 때마다 관련 내용을 직접 수정해야 했기 때문에 콘텐츠 관리도 번거로운 편이었다.

또 하나 아쉬웠던 점은 나라는 사람에 대한 정보가 충분하지 않다는 것이었다.

포트폴리오는 단순히 결과물을 보여주는 공간이 아니라, **어떤 문제에 관심을 가지고 있고 어떤 방식으로 디자인하는 사람인지 전달하는 공간**이기도 하다고 생각한다.

그래서 이번 리뉴얼에서는 세 가지를 중요하게 생각했다.

첫째, 방문자가 프로젝트를 한눈에 파악하고 관심 있는 작업을 쉽게 찾을 수 있어야 한다.

둘째, 프로젝트가 늘어나더라도 새로운 콘텐츠를 추가하거나 수정하기 쉬운 구조여야 한다.

셋째, 작업 결과물뿐 아니라 나의 강점과 디자인에 대한 생각도 자연스럽게 전달할 수 있어야 한다.

특히 일본에서 UX/UI 디자이너 취업을 준비하고 있지만 한국어와 영어를 사용하는 사람들에게도 사이트를 공유할 일이 있기 때문에, 일본어·한국어·영어의 3개 언어를 지원하도록 설계했다.

## 02. 프로젝트를 더 쉽게 탐색할 수 있도록

이번 사이트에서 가장 먼저 개선하고 싶었던 부분은 프로젝트 탐색 경험이었다.

기존에는 방문자가 개별 프로젝트를 순서대로 확인해야 했다면, 새 사이트에서는 전체 프로젝트를 카드 형태로 배치해 어떤 작업이 있는지 한눈에 볼 수 있도록 했다.

각 프로젝트에는 카테고리와 태그를 부여하고, 이를 바탕으로 원하는 작업을 찾을 수 있도록 필터와 검색 기능을 추가했다.

예를 들어 특정 분야의 프로젝트만 보고 싶을 때는 카테고리 필터를 사용할 수 있고, 프로젝트 이름이나 관련 키워드를 알고 있다면 검색을 통해 바로 찾을 수 있다.

프로젝트별 상세 페이지도 새롭게 구성했다.

각 상세 페이지에서는 프로젝트의 개요와 담당 역할, 제작 기간, 사용한 도구 등을 확인할 수 있으며, 이미지 갤러리를 통해 작업 결과물을 살펴볼 수 있다.

또한 프로젝트마다 고유한 URL을 부여했다.

다른 사람에게 포트폴리오를 전달할 때 전체 사이트가 아닌 특정 프로젝트만 공유해야 하는 경우도 있기 때문이다.

상세 페이지 하단에는 다른 프로젝트도 함께 확인할 수 있도록 구성해, 하나의 프로젝트를 본 뒤 자연스럽게 다른 작업으로 이동할 수 있도록 했다.

### 프로젝트뿐 아니라 기록도 함께

이번 리뉴얼에서는 프로젝트 외에 개인적인 경험과 생각을 정리할 수 있는 Notes 페이지도 추가했다.

프로젝트 상세 페이지가 디자인 결과물과 제작 과정을 보여주는 공간이라면, Notes는 인턴십이나 팀 프로젝트 회고, 디자인과 개발을 하면서 배운 점 등을 조금 더 자유롭게 기록하는 공간이다.

글마다 커버 이미지와 본문 이미지를 사용할 수 있도록 구성했고, 목록에서 글을 선택하면 개별 상세 페이지로 이동하도록 했다.

포트폴리오에 모든 경험을 담기보다는 프로젝트와 글의 역할을 구분하고 싶었다.

프로젝트에서는 무엇을 만들었는지 보여주고, Notes에서는 그 과정에서 어떤 생각을 했고 무엇을 배웠는지 조금 더 자세히 전달하는 방식이다.

## 03. 콘텐츠를 관리하기 쉬운 구조로 개발하기

사이트의 주요 콘텐츠는 프로젝트 정보와 이미지, 소개 글처럼 자주 변경되지 않는 정적인 데이터다.

회원가입이나 로그인, 서버에 데이터를 저장하는 기능이 필요하지 않았기 때문에 별도의 백엔드를 구축하지 않고 **HTML, CSS, JavaScript 기반의 정적 웹사이트**로 개발하기로 했다.

배포에는 기존에도 사용해 본 적이 있는 Vercel을 활용했다.

개발하면서 특히 신경 쓴 부분은 콘텐츠 관리 방식이었다.

프로젝트마다 정보를 직접 HTML에 작성한다면 새로운 프로젝트를 추가할 때마다 페이지 구조를 수정해야 한다.

그래서 프로젝트의 이름과 설명, 카테고리, 태그, 제작 기간, 이미지 경로 등을 데이터로 관리하도록 구성했다.

이미지 역시 프로젝트별 폴더로 구분해 관리하고, 필요한 데이터를 추가하면 프로젝트 목록과 상세 페이지에 반영할 수 있도록 했다.

Notes도 동일한 방식으로 목록과 상세 페이지의 콘텐츠를 관리할 수 있도록 했다.

이렇게 구성하니 새로운 작업을 추가하거나 기존 내용을 수정할 때 페이지 레이아웃을 직접 편집할 필요가 줄어들었다.

또한 다국어 지원을 위해 일본어·한국어·영어 콘텐츠를 구분해 관리하고, 사용자가 언어를 전환하면 해당 언어의 텍스트가 표시되도록 구현했다.

이미지를 불러오는 동안에는 쉬머(Shimmer) 효과가 적용된 플레이스홀더를 표시하도록 했다.

이미지가 많은 포트폴리오의 특성상 네트워크 환경에 따라 로딩 시간이 달라질 수 있기 때문에, 이미지가 표시되기 전에도 콘텐츠의 영역을 미리 파악할 수 있도록 고려했다.

처음부터 대규모 서비스처럼 복잡한 구조를 만들기보다는, **현재 필요한 기능을 충족하면서 앞으로 콘텐츠를 추가하기 쉬운 형태**로 설계하는 데 집중했다.

## 04. Figma와 Codex로 진행한 4일간의 제작

이번 사이트는 기획과 디자인에 2일, 개발에 2일을 사용했다.

디자인은 Figma로 진행했고, 실제 웹사이트 구현에는 Codex Work를 활용했다.

약 1년 전 처음 포트폴리오 사이트를 만들었을 때는 React를 사용해 직접 코드를 작성하고 수정했다.

반면 이번에는 자연어로 요구사항을 전달하면서 코드를 생성하고 수정하는 방식으로 개발했다.

프로젝트 목록과 상세 페이지, 필터와 검색, 다국어 전환 등 필요한 기능을 설명하고, 구현된 결과를 직접 확인하면서 수정 사항을 전달했다.

디자인한 화면을 코드로 구현하는 과정이 이전보다 훨씬 빨라졌다는 점이 인상적이었다.

하지만 AI가 생성한 코드가 항상 Figma의 디자인과 일치하는 것은 아니었다.

### 생각보다 어려웠던 디자인과 구현 결과의 차이

가장 자주 겪었던 문제는 Figma에서 설계한 화면과 실제 브라우저에서 표시되는 화면이 다르게 보이는 것이었다.

레이아웃의 간격이나 요소의 크기가 미묘하게 달라지기도 했고, 디자인에 포함하지 않았던 요소가 추가되는 경우도 있었다.

처음에는 단순히 'Figma 디자인과 똑같이 수정해 줘'라고 요청했지만, 이러한 지시만으로는 원하는 결과를 얻기 어려웠다.

AI가 어떤 부분을 수정해야 하고 어떤 부분은 그대로 유지해야 하는지 명확하게 알기 어려웠기 때문이다.

그래서 점차 요청하는 방식을 바꾸기 시작했다.

단순히 화면이 다르다고 이야기하는 대신, 변경해야 할 요소의 크기와 여백, 정렬 방식 등을 구체적으로 전달했다.

또 수정이 필요하지 않은 부분은 기존 디자인을 유지하도록 명시했다.

예를 들어 카드의 간격을 수정하고 싶다면 카드 사이의 간격만 변경하고 이미지 비율이나 텍스트 스타일은 유지하도록 요청하는 식이었다.

구현 결과를 확인하고, 수정할 부분을 정리해 다시 전달하는 과정을 반복했다.

이 과정에서 느낀 것은 **AI를 활용한 개발에서도 디자인 의도를 정확하게 전달하는 능력이 중요하다**는 점이었다.

코드를 직접 작성하지 않더라도 어떤 결과물이 필요한지 판단하고, 문제가 발생한 부분을 구체적으로 설명하는 과정은 여전히 필요했다.

## 05. AI를 사용하면서 달라진 개발 방식

이번 리뉴얼에서 가장 크게 체감한 변화는 개발 과정에서 직접 코드를 작성하는 비중이 줄었다는 것이다.

약 1년 전에는 원하는 기능을 구현하기 위해 관련 코드를 찾아보고, 직접 작성하고, 오류가 발생하면 원인을 분석하면서 수정했다.

이번에는 자연어로 기능과 디자인 요구사항을 전달하고, AI가 작성한 결과를 확인하는 방식으로 작업했다.

특히 프론트엔드 개발 경험이 있었기 때문에 생성된 화면을 보면서 어떤 부분에 문제가 있는지 비교적 쉽게 판단할 수 있었다.

레이아웃이 의도와 다르게 구현되었을 때도 어떤 속성이나 구조를 수정해야 할지 예상할 수 있었고, 이를 자연어로 구체적으로 설명하는 데 도움이 되었다.

반면 새로운 어려움도 있었다.

### 생각보다 빠르게 소모되는 크레딧

Codex Work를 사용하면서 예상보다 크레딧이 빠르게 소모된다는 점을 알게 되었다.

작은 UI 수정이라도 요청을 여러 번 반복하면 사용량이 누적되기 때문에, 무작정 수정과 확인을 반복하는 방식은 효율적이지 않았다.

그래서 요청하기 전에 어떤 부분을 수정해야 하는지 먼저 정리하고, 관련된 변경 사항은 가능한 한 함께 전달하려고 했다.

또한 수정이 필요한 요소와 유지해야 할 요소를 명확히 구분해 불필요한 변경이 발생하지 않도록 신경 썼다.

결국 AI를 활용한 개발에서는 단순히 프롬프트를 많이 작성하는 것보다, **필요한 작업을 정확하게 정의하고 한 번의 요청으로 의도를 충분히 전달하는 것**이 중요하다는 생각이 들었다.

프롬프트 작성 역시 개발 과정의 일부가 된 셈이다.

## 06. 포트폴리오 리뉴얼을 마치며

이번 리뉴얼은 약 1년 전 제작했던 사이트를 다시 만들면서 그동안 달라진 나의 작업 방식과 개발 환경을 돌아볼 수 있었던 경험이었다.

프로젝트와 글을 데이터로 관리하는 구조를 만들고, 검색과 필터, 다국어 지원 등 이전 사이트에 부족했던 기능을 추가했다.

무엇보다 사이트를 보기 좋게 만드는 것뿐 아니라 앞으로 콘텐츠를 어떻게 관리하고 활용할 것인지 고려하면서 설계할 수 있었다.

개발 과정에서는 Codex를 활용해 직접 코드를 수정하는 작업을 크게 줄일 수 있었다.

하지만 그만큼 원하는 결과를 명확하게 설명하고, 생성된 결과물이 의도한 디자인과 일치하는지 확인하는 과정이 중요해졌다.

실제로 Figma와 구현 화면 사이의 차이를 수정하면서, 막연한 요청보다는 구체적인 수치와 변경 범위를 전달하는 편이 효과적이라는 것을 알게 되었다.

또 AI 도구를 사용한다고 해서 항상 작업이 효율적으로 진행되는 것은 아니었다. 크레딧과 반복 작업에 드는 비용을 고려하면서 요청을 정리하는 과정도 필요했다.

이번 프로젝트에서 느낀 것은 **AI가 코드를 작성하는 과정은 도와줄 수 있지만, 무엇을 만들고 어떤 결과를 원하는지 결정하는 역할은 여전히 사람에게 있다는 점**이었다.

앞으로도 프로젝트가 늘어나고 새로운 경험이 쌓일 때마다 포트폴리오 사이트를 계속 업데이트할 예정이다.

이번에는 그 작업을 조금 더 쉽고 빠르게 할 수 있는 기반을 마련했다는 점에서 만족스러운 리뉴얼이었다.
